# UB 按需分配：让一个 tile 装下更多有效数据

先从基线 DAS 和 tiling 结果记录每个 tile 处理的行数、总 tile 数、block_dim，以及限制 tile 的原因。只有 UB 是限制因素时，压缩缓冲才可能直接增大 tile。如果实际受指令长度、维度整除或并行度限制，先保留原分块作对照。

## 生成 builder 时能做什么

- **保留紧凑输入。** 例如四行 FP32 激活共用一行 BF16 权重。若选中的指令可以复用这一行，保留权重的单行 shape，在消费处使用；需要展开成四行的指令则按四行计。比较紧凑加载和搬运时广播两种表达，前者可能节省 UB，后者可能节省 Vector 指令。
- **缩短大临时值的存活区间。** 从最后一次使用往回看，尝试让独立分支的生产者靠近消费者，避免两份宽类型中间结果同时存活。核对 pass 后的实际顺序。保留算子要求的 FP32 累加、舍入位置和训练输出。
- **先算字节再调 tile。** 对上述权重，假设每行 1024 个元素且已满足对齐，按四行 BF16 预留是 8192 B，按一行是 2048 B。只有这 6144 B 落在原来的占用峰值上，并足以容纳更大 tile 所需的额外输入、输出和 scratch，实际行数才可能增加。

## 需要改 DVM 分配器时

1. 对候选 tile 列出每个缓冲的 dtype、对齐后的物理跨度、分配起点、首次写入和最后一次使用。按实际 dtype 把元素换算成字节。为 pad、向量指令读写的完整范围和工作区留空间。归约结果即使只有一个元素，若对应指令用整块输入大小的 scratch，仍按其真实访问范围分配。
2. 在同一时刻，对每块独立活跃存储只计一次。共享地址的别名要跟到最后一个消费者；异步搬运要跟到完成事件，双缓冲在重叠阶段要计两个槽。仅当旧值已释放、容量与对齐都满足时，才把地址给新值复用。
3. 让 tiler 的容量估算和 codegen 的实际地址使用同一套字节计算。在目标 DVM checkout 查 `src/kernel.cc` 的 `Analyze`、`TileSizeLimit` 与 `CodeGenHelper`，以及 `src/ops.cc` 的 `GetDynXBufBegin`。先更新 tile 对应的对齐 stride，再计算紧凑缓冲和后续 workspace 的起始地址；保留 `NeedFullXbuf()` 等要求整块分配的分支。将峰值与扣除代码及固定预留后的 UB 预算比较，各项预留只扣一次。

## 验证省下的空间用到了哪里

先固定 tile，对照前后分配区间，检查末地址在 UB 范围内、同时存活的独立缓冲互不覆盖。再让 tiler 重新选块，对照实际行数、尾块、tile 数、核数和完整算子耗时。优先测刚好能多放一行的 shape 及其两侧，并用混合 dtype、非对齐尾块、多消费者或动态 shape 切换覆盖受影响的路径。输出按原 PyTorch 算子校验；单核 tile 变大而总耗时变差时，检查并行度是否下降。
